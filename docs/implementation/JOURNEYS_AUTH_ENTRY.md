# Journeys Auth entry

Journeys uses the existing approved Supabase identity through its server client. New bilingual routes are `/{locale}/sign-up`, `forgot-password` and `reset-password`. Links and actions retain a bounded, locale-safe next path, reject authentication loops and never automatically import a device draft.

Signup follows provider confirmation policy. An immediately confirmed local account returns to its task; a confirmation-required response displays a conditional acknowledgement, not a claim of message delivery. Known/unknown password-recovery requests have the same conditional acknowledgement and retry entry. Provider rate limits remain in effect. New passwords require at least eight characters, matching the existing application; provider strength requirements still apply.

Recovery uses an Auth-verified PKCE code or a recovery-type OTP. A 15-minute HTTP-only, same-site server ticket is bound to the verified user/session and original locale/next. A query value, ordinary password login, forged ticket, different account/session or expired ticket cannot authorize a reset. An active account must explicitly sign out before consuming another recovery credential. Password update is delegated to Auth; no custom user table or migration is introduced. Callback responses and account pages remain private/no-store and noindex.

Deployment configuration: set `KINNSO_AUTH_RECOVERY_SECRET` to a server-only random value of at least 32 characters, identical across serving instances. Do not expose it through NEXT_PUBLIC variables or GitHub/public artifacts. Rotation expires pending tickets; request a fresh link. Missing configuration leaves recovery unavailable while signup/sign-in remain usable. Keep `KINNSO_SITE_URL` bound to the exact application origin and retain the existing `/callback` redirect alias including locale/flow/next query parameters through the Auth provider. Default PKCE mail must be opened in the browser that requested it. Custom OTP templates must use the verified recovery/email type supported by the callback. These are reviewable configuration requirements, not evidence that production settings were changed.

The isolated local runner generates an ephemeral server ticket key after container ownership verification. Its existing confirmation-disabled Auth and admin-generated synthetic verification links prove credential handling only. Actual confirmation mail, recovery delivery, slow external mailbox behavior, hosted callback allowlist and human U01/U03 remain blocked until a named mailbox and environment are accepted. No production fixture, email request or provider configuration change is part of the local suite.

Rollback: revert the Auth entry PR; retain all accounts and stored device drafts. Remove the added server setting only after serving the reverted application. Original sign-in and RPC authorization continue using the same Auth service.
