# Merchant invitation service contract

N11/F08/G04/G11/G12/U04 adds an invitation contract to the existing merchant service. It uses canonical live Supabase sessions, the provider-verified recipient email, existing company ownership/member/branch tables, and shared atomic request receipts and merchant audit. There is no separate user store, global account lookup, provider mail send or financial operation.

The owner creates a limited invitation with an explicit private label, recipient email, marketing/clerk/finance role, currently active company branches and audit reason. The token input must be64 lowercase hexadecimal characters generated from32 cryptographically random bytes. Only its SHA256 digest and a per-token salted normalized email digest are stored. The raw token and normalized email are excluded from server receipts, automatic audit content and returned directory/preview DTOs. The private owner label and explicit reason remain owner-authored data. The proposed default is24-hour expiry and at most100 pending invitations per company, serialized transactionally; production policy approval is still required.

Owner create/revoke/list and receipt replay all recheck current company ownership. The directory returns at most50 records per validated company UUID keyset, including truthful pending/accepted/revoked/invalidated/expired status. A narrowly scoped profile trigger permanently timestamps unused-invitation invalidation on ownership change or suspension. Returning to a former owner or active status cannot revive an old token; unrelated profile edits preserve it. The timestamp records system invalidation without inventing an audit actor for out-of-band admin SQL. Related owner labels do not imply a global user/email directory. Repeated cancellation records one audit. An accepted invitation cannot revoke a membership; the existing member editor performs explicit offboarding.

Only the currently verified intended recipient can preview or accept. Preview writes nothing and describes the role and branch scope. Acceptance rechecks the active issuing owner, expiry/revocation and active assigned branches, then consumes the token and inserts a previously absent membership, audit and request receipt in one transaction. Concurrent acceptance has one winner. Two invitations cannot overwrite an existing role. Existing or inactive memberships require the owner editor; invitations never upsert or reactivate them. Ownership transfer, unverified/changed email or missing canonical session denies acceptance.

Exact accepted-request replay can acknowledge its historical receipt only while the recipient's current membership still authorizes access. A new request cannot reuse a consumed token; an offboarded member using the same JWT and old receipt remains denied. Replay does not grant permissions. The subsequent workspace always reads current authoritative access.

Future UI/BFF integration must keep raw tokens only in transient memory and the invitation URL fragment, exclude them from query strings, OAuth `next`, logs, localStorage and public caching, and retain the same request/body for an uncertain outcome. Manual link sharing is not evidence of email delivery. This source increment implements RPC/integration contracts; invitation UI/BFF and hosted role acceptance remain separate pending tasks.

The additive migration creates one private RLS table, two revoked internal helpers, one revoked trigger function/profile trigger and four authenticated-only RPCs. No direct API table grants, anonymous/service-role execute, Auth/Storage schema replacement or existing member/write/RPC replacement. Production SQL application, recovery checks and policy acceptance require their own exact review. Source/local tests, merge, public release and named U04 acceptance are separate states. Rollback UI/BFF consumers while retaining accepted memberships, request receipts and audit; do not drop written invitation data or restore an old backup over later production writes.
