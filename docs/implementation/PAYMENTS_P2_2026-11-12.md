# Phase 6 P2 — fake hosted checkout and traveller pay surface

**Status:** deployed and verified in production, inert (flag off). Release `8a6c827`, ledger **271** (`20261111130000`), deployment `dpl_H488dwTCNjypbXTBobc8HRDdNqrt`.

## What shipped

- A provider seam (`lib/payments/provider.ts`): `fake` hands the traveller to our own labelled test-checkout page, `stripe` creates a hosted Checkout Session server-side (line item, locale return URLs, metadata), and anything else is unconfigured and refuses. The amount is always the server-side snapshot; the browser never supplies it.
- Owner-only RPCs: `kinnso_traveller_payment` (read by request or payment), `kinnso_traveller_start_checkout` (flag/window/status lock, records the session through the app), `kinnso_traveller_record_checkout`, and `kinnso_traveller_confirm_fake_payment` (fake only, one-way, replay-safe). A closed window is returned as a soft `expired` result so the expiry updates commit instead of being rolled back by an exception.
- The traveller pay surface: accepted priced trips show the amount, deadline and a Pay action; paying opens the hosted checkout, confirming returns to the request list with a "payment received" state and a Paid row. When ops disables the flag the action is replaced by paused copy and direct checkout refuses.
- Both booking lists now carry the payment id/status/amount/currency/deadline; a paid trip also appears in "starting soon". The creator inbox shows the amount and payment state on accepted trips.
- `GET /api/booking-requests/[id]/payment`, `POST /api/booking-requests/[id]/payment`, `GET /api/payments/fake/checkout/[paymentId]` (test-mode HTML, no card fields), `POST /api/payments/fake/confirm` (JSON or form; form redirects back). The fake surface is hard-limited to `paymentsProvider().name === 'fake'`; production reports provider `none` and `providerConfigured: false`.

## Limits

- Only the fake provider is exercised end to end. The Stripe hosted-checkout request is implemented and unit-tested against a stand-in API, but has not touched a real Stripe account — that is P5 (account/KYC, live/test keys in Vercel, webhook secret).
- No webhook yet: a real Stripe redirect is not proof of payment. Those rows stay open until the P3 webhook marks them paid; the fake confirmation exists only so the local flow can complete.
- `KINNSO_PAYMENTS_PROVIDER` and `STRIPE_SECRET_KEY` must be configured server-side before enabling payments; with the flag on and no provider the start endpoint refuses with 503 rather than creating a session.
- The 7-day window is created at acceptance and swept only when ops runs the expiry RPC; there is no scheduled sweeper yet.
- Refunds (fake-only), receipts, traveller-visible prices outside the pay panel, and account data-rights handling for payment records remain P4/P5 work.
