## Explicit worker database acceptance

Run only on an approved synthetic local project accepted by `scripts/verify-kinnso-target.ts`. `kinnso-v3` at `http://127.0.0.1:54421` is accepted only in canonical CI (`CI=true`); existing approved isolated local projects use `http://127.0.0.1:58421`. An operator must attest `KINNSO_WORKER_TEST_DATA=synthetic`; this flag alone cannot authorize a target. The guard also verifies actual Docker labels, owned database volume, bound gateway port, network and auth/REST destinations, plus JWT signatures/roles against the attested services. Environment intent and the inspected target must agree.

The worker guard resolves `DOCKER_CONTEXT`, explicit `DOCKER_HOST`, or the implicit current context using Docker's precedence. It requires a local Unix socket and OS peer/namespace evidence, then pins the canonical endpoint and CLI environment for every inspection, routing, key and port check. Remote transports (including loopback TCP tunnels), mounted sockets serving a different network namespace, unavailable evidence and endpoint replacement fail closed before clients/hooks. MySQL independently repeats this proof and requires the same daemon/socket/client namespace as the Supabase attestation.

Peer proof requires Python 3 (isolated mode). Native Linux Docker must serve the socket in the client's network namespace; `/proc` evidence must be readable. For systemd socket activation, peer credentials identify the listener creator (root PID 1), so the guard additionally requires local system-manager evidence that the active `docker.socket` listener matches the pinned path and activates the running `docker.service` dockerd with `fd://`, matching service cgroup and client network namespace. RootlessKit's builtin driver is accepted when its parent in the client namespace owns the published IPv4 listeners. Docker Desktop is accepted when its local backend serves the API socket and owns those listeners (`ps`/`lsof` are also required on macOS). Other proxies, platforms, drivers or inaccessible/ambiguous evidence fail closed; changing an environment flag cannot bypass proof. Offline regressions mock Docker, clients and all peer-proof OS/socket/system-manager reads; no daemon or configured database is used.

Supply local credentials and target settings in the worker's `.env.test` or environment. Never copy cloud credentials into these files. Existing aliases such as `NEXT_PUBLIC_SUPABASE_URL` must also match the approved origin. Require both anon and service-role JWTs, even for sync, so a mixed credential set fails before client construction. Secrets and Docker stderr are never included in guard errors.

KINNSO_WORKER_TEST_DATA=synthetic pnpm --filter @kinnso/scan-app test:integration

This optional actual-MySQL contract was not run locally; offline reader regressions and attestation tests passed.

## Grant migration and future release ordering

Forward: `supabase/migrations/20261028090000_aud_02_server_only_rate_limits.sql`. It atomically revokes PUBLIC/anon/authenticated execution of both limiter RPCs and direct browser table grants, preserving service-role EXECUTE and all buckets. It changes no function signature, quota size or product-data permission. CI exports the local service-role key under its server-only environment name for guest-flow acceptance.

The server-only helper uses a separate nonpersistent service client solely for ledger RPCs, derives a trusted ingress IP and applies fixed agent (20/hour) or checkout (5/10 minutes) policy. Session clients still resolve identities, read product data, persist messages/bookings and run tools. Vercel deployments use the overwritten `x-vercel-forwarded-for` IP; missing/malformed headers and non-Vercel servers share `unknown`. A future non-Vercel deployment must establish a trusted ingress contract before enabling per-IP buckets; arbitrary request headers are insufficient.

When a release is separately authorized, verify the server service key is available, release both application callers, then apply the grant migration on the approved target. Applying grants before compatible callers temporarily closes agent/checkout requests. Missing key, RPC error or transport failure fails closed before model/Stripe work. Rehearse with synthetic data first; no production readiness claim is made here.

## Rollback

Prefer a source revert **only with compatible server quota callers retained**. Reverting to the old session-client calls while revocation remains active causes agent/checkout failure. Reverting webhook bounds or test guards reopens the corresponding vulnerability and should be avoided independently of quota compatibility.

Emergency compatibility SQL is in `supabase/rollbacks/20261028090000_aud_02_server_only_rate_limits.sql`, outside the automatic forward migration directory. It restores anon/authenticated EXECUTE only; service-role access already existed through the repository's default grants. No rows, table grants, RLS or function definitions are rewritten. The rollback intentionally reopens AUD-02 (caller-selected victim IP/negative window), so it requires a separately authorized release decision. Coordinate it with any application revert; reapply the forward migration after recovery. Offline rehearsal verified rollback/reapplication without bucket loss. No rollback was run against an existing configured database.
