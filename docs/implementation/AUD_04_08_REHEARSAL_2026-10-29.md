# AUD-04 / AUD-08 reservation proof and rollback

Source baseline: `2dc9cc2bde38607dd9956c69c3723c124daffc98` (`main`). Candidate branch: `codex/aud-04-08-quota`. Source remediation only; no migration or worker deployment has been performed on a hosted/configured target.

## Reservation contract

`reserve_worker_launch` is the sole quota decision for initial scans, scan retries, initial verification and verification retries. The worker authenticates requests; verification still checks submission ownership or active ops membership. Ops requests reserve the **submission owner's** budget. The service-only RPC revalidates job/submission ownership, locks the creator row before any job mutation, checks live jobs and a single durable launch ledger, and commits job creation/reset with one reservation. Each request runs in the normal PostgreSQL READ COMMITTED transaction used by PostgREST. Different processes/replicas share the same owner lock and ledger.

Existing budgets remain separate by kind within this one mechanism:

| Kind | Live jobs per owner | Launches per trailing 24 hours |
|---|---:|---:|
| Scan | 1 | 3 |
| Verification | 3 | 20 |

Retries consume a new reservation even when they reuse a job row. Failure, process restart, or job deletion does not refund it. The scan's bounded internal LLM retry remains part of one reserved run. Reservation transport failures or malformed responses never launch a pipeline. The ledger has RLS enabled, no browser access and no direct service-role mutation grant; only the service role can execute the reservation RPC. Existing job owner-read RLS and active-job unique indexes are unchanged.

A reservation remains charged when the process dies after commit and before launching work: this intentionally favors the spend ceiling over refunding an unknown outcome. Stale jobs (15 minutes without progress) stop consuming concurrency; the RPC retires them within the reservation transaction so existing unique indexes permit recovery. Staleness does **not** refund daily budget. Entries at or before the trailing-24h cutoff stop counting, without deleting history. No background ledger pruning/retention job is introduced.

## Forward cutover (separate release authorization required)

1. Stop **all** old worker replicas and block scan/verification launch ingress. Keep launch ingress paused for at least **24 hours** after the last old-worker launch; drain/stop any remaining old work before cutover. The legacy code did not persist retries, so no migration can reconstruct its true daily spend. A rolling deployment with old writers would bypass the new reservation boundary. This pause avoids claiming an unknown historical allowance is available.
2. Follow the existing exact-target, recovery/export/restore and reviewed-transaction gates in `scripts/MIGRATION_RELEASE.md` for a separately approved target. Apply only the new migration `20261029090000_aud_04_08_worker_launch_reservations.sql`. Do not edit or replay the historical verification migration. The migration backfills each job's most recent known created/started timestamp as additional protection, not as proof of complete historical retry accounting.
3. Regenerate DB types from the approved isolated schema for validation; deploy the new worker while launch ingress stays blocked. Validate service-role RPC access, browser denial, quotas, retry recovery and the owner/ops boundary on the approved synthetic target. Resume ingress only with all writers using reservations. This task authorizes no live cutover, feature activation or production deployment.

## Rollback

Stop/drain all new worker replicas and block ingress before applying `supabase/rollbacks/20261029090000_aud_04_08_worker_launch_reservations.sql` in a reviewed transaction. It removes the RPC and intentionally **retains** the additive ledger table, index, RLS and restrictive grants. It changes no job/submission/DNA data and discards no launch history. New workers fail closed while the RPC is absent. Do not drop or truncate the ledger as part of rollback.

Source rollback is a normal revert, but the old worker restores AUD-04/08 weaknesses. Keep launch ingress disabled unless the operator explicitly accepts that regression. Retaining the ledger is deliberate: operational rollback disables the feature without destructive schema/data cleanup.

To re-enable the fixed worker after that rollback, apply the **function definition and following grants only** from the forward migration (the suffix starting `create function public.reserve_worker_launch`) in one reviewed transaction. Do not replay `CREATE TABLE` or backfill against the retained ledger. The isolated proof executes this exact rollback/reapplication sequence and verifies job/history preservation. Any later destructive ledger removal is a separate reviewed data-retention action.
