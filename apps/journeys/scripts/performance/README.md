# Local mobile performance lab

Use Node 22.19 or later. Install the optional auditor separately from product dependencies:

```sh
npm ci --prefix scripts/performance --ignore-scripts
npx playwright install chromium
npm run build
node scripts/performance/run.mjs
```

The runner requires the existing approved `.env.test`, verifies the owned isolated Supabase project/container, and starts its own production build on loopback port 3521. An occupied port fails closed. It never targets a cloud URL. It creates one synthetic local author, an explicitly authored guide and a persisted trip; cleanup deletes only that owned actor and cascading fixtures. Do not supply production credentials.

It measures home, explore, guide and the signed-in trip editor three times each with cold and warm browser HTTP cache. Every pair gets a fresh browser context; the trip's login cookies are retained when clearing HTTP cache. The app process and database stay warm. Chrome uses a 390×844 mobile viewport, 4× CPU slowdown, 150 ms network latency, 1,600 Kbps download and 750 Kbps upload. Lighthouse uses applied DevTools throttling, not simulated scores. External HTTP requests are blocked and recorded.

Each navigation retains its Lighthouse report, LCP, CLS, TBT, JavaScript/image transfer bytes and browser API timings before asserting success. Actual search/filter/draft/persisted-note interactions retain traces and assertions. Trace arguments are removed; timestamps, categories and durations remain. Artifacts stay in ignored `evidence/performance/`. The overall assessment requires all navigation, interaction, backend-read and cleanup evidence; missing or failed evidence cannot pass. The median targets are LCP ≤2.5 s and CLS ≤0.1 for each page/cache group; `report.json` reports failure without rewriting measurements. A successfully collected failing target is still useful evidence, so the process exits nonzero for collection/cleanup failures, not merely a slow target.

Query timing separately executes three equivalent backend reads per core page using the real local catalog projection/guide/trip RPCs. This includes HTTP/PostgREST overhead; isolated PostgreSQL execution time remains unmeasured. API timings are local browser observations, not cloud/query p95. Interaction elapsed time is not field INP. A synthetic guide with no cover does not measure real image delivery. Production, physical-device and human accessibility acceptance remain separate gates.

For a separate warm-read latency baseline, run `node scripts/performance/run-latency.mjs` after building the current committed source. This runner owns loopback port 3523 and one synthetic actor. It inserts 2,401 published summaries, publishes one explicitly authored day/stop, and adopts it into a real trip. The observed PostgREST row cap must be less than half the dataset. Every catalog response is bounded and verified, and guide/trip identity and the persisted trip aggregate are checked.

Each of home, filtered explore, guide and trip gets 3 retained warmup reads and 40 measured reads for each layer: BFF API, direct PostgREST, and PostgreSQL `EXPLAIN ANALYZE`. These profiles use the corresponding anon/authenticated role in a READ ONLY transaction ending with ROLLBACK. The operations merchant exception is described below. Reports keep planning/execution times and redacted plans, including the RPC total; they do not claim to expand individual statements inside PL/pgSQL. Instrumentation overhead, shared warm buffers and exclusion of SQL result serialization/network are explicit. No database reset, restart, cache flush, ANALYZE mutation or other actor cleanup occurs. Actor/guide/trip absence is verified after owned cleanup.

The initial run returns `MEASURED_BUDGET_NOT_SET`. A provisional local engineering budget may then be supplied through `KINNSO_LATENCY_BUDGET_FILE`, an ignored JSON file containing `environment: "owned isolated local"`, `project`, the exact `sourceSha`, absolute `baselineFile`, its `baselineSha256`, and positive millisecond `limits` for `api`, `postgrest` and `postgres`. The source-bound baseline must be complete. The nearest-rank p95 uses at least 40 distinct verified samples per group; a missing sample, failed assertion or cleanup cannot pass. Budgets are local regression limits and grant no cloud SLO or provider activation authority. Baseline reports, failed attempts and warmups stay retained separately; this runner does not replace the mobile navigation lab or production acceptance.

Foundation guide/trip are demo screens and explicitly not comparable to current durable behavior; home/explore also have different datasets. Same-condition deltas show shell delivery cost, not a claim of functional or content parity. Baseline collection/comparison that has not run remains `NOT_RUN`.

`--trip-only` collects three cold/warm pairs for the trip screen. Its report remains `INCOMPLETE` because the other core pages are missing; it exits nonzero and cannot serve as complete acceptance on its own. Preserve failed invocations and record the source reports and exact sample selection when combining unchanged-condition observations.

## P16 operations continuation

Run `node scripts/performance/run.mjs --operations` and `node scripts/performance/run-latency.mjs --operations` after building the exact candidate. The complete operations profiles retain all four traveller pages and add authenticated creator list/detail and merchant-owner campaign/review pages. The owned fixture contains55 campaigns,55 accepted creator collaborations and one submitted original deliverable; all fixture actors are created inside the verified local project and only their records are cleaned up. Private navigation verifies the actual signed-in actor. Reports separate anonymous/creator/merchant-owner roles and cold/warm browser HTTP cache; server/database buffers remain warm.

Each operations navigation gets three cold/warm pairs with the existing390x844,4xCPU,150ms/1600Kbps/750Kbps conditions; every interaction and equivalent backend read remains required. Filter/evidence-editor/review-feedback interactions preserve source state and do not claim an approval/payment action. Warm latency retains3 warmups plus40 verified reads for API/PostgREST/PostgreSQL. Traveller and creator profiles retain READ ONLY/ROLLBACK. Only merchantCampaigns and merchantReview use READ WRITE/ROLLBACK, allowing the existing query_kinnso_merchant_campaigns read RPC to acquire its shared authorization locks. The builder accepts only eight named read profiles, validates matching authenticated fixture claims and UUID bindings, constructs its own SQL, and always ends with ROLLBACK; it accepts no supplied SQL, command RPC or transaction mode. The existing localhost/container ownership gate remains mandatory. Product functions, authorization locks and capabilities are unchanged. Every PostgreSQL sample records its actual transactionMode. Missing private pages, mismatched roles, incomplete datasets or cleanup fail the complete assessment. Earlier READ ONLY/shared-lock failures remain historical failures; the method changed, so those groups cannot provide a controlled before/after latency comparison. A future change to the allowlisted RPC or its callees needs a fresh side-effect review.

The owned Ubuntu CI collection uses the same locked tooling and records its actual platform; it is not comparable to older Windows runs without matching conditions. Collection success and provisional local LCP/CLS targets are separate, and no production SLO or field CWV threshold is accepted. Retain failures and exact source/merge/tree provenance before choosing an optimization. Real covers, hosted latency, physical devices, concurrency and human acceptance remain separate gates.

Operations navigation records a started/failed sample before calling Lighthouse. The45-second page-load setting is unchanged; a separate60-second Lighthouse gather/audit deadline makes a stalled call fail with null/unverified metrics while the owned cleanup/artifact window remains available. A late result cannot backfill that failed sample. The deadline is retained in comparison conditions. It does not reduce48 required navigations,8 interactions,24 equivalent backend reads or960 latency samples. Current owned artifacts must still prove actual cleanup and denominators.

A failure after fresh actor verification is retained for its pair while later independent pairs, interactions and backend reads are attempted. A failed cold call leaves that pair warm slot missing; there is no retry or late-result backfill. Initial setup/authority failure still aborts. The first error and every collection failure remain in the report, so useful later samples never turn the complete assessment into PASS.

Each navigation also retains elapsed collection time, page DOM/load event counts, owned request completion/failure counts and up to10 pending request summaries. Only known route shapes are retained, UUIDs become OWNED_ID, Next assets become /_next/ASSET, and unknown paths become OTHER_OWNED_REQUEST. Query strings, origins, headers, claims, bodies and error payloads are not exported. Counts include Lighthouse's own blank/navigation lifecycle; this is collection-stage evidence, not an extra web-vital metric. Listeners belong to that page and are removed before its immutable snapshot is saved, including on timeout. The diagnostic version is part of comparison conditions. The trace-engine warning seen on successful samples does not establish the cause of warm timeouts; retained lifecycle evidence must locate the failing stage first.


The collector now handles only an owned synthetic fixture's beforeunload warning during Lighthouse's initial main-frame blank reset. Lighthouse13.5.0 performs that reset before installing its own dialog handler; the locked-driver loopback probe reproduces a blocked blank transition with zero DOM/load events and one pending fetch, and controlled acceptance releases it. The page handler is removed at the first main-frame about:blank and again on every collection exit. It does not accept confirm/prompt/alert dialogs or dialogs from a foreign origin, and a stopped collector cannot start a queued acceptance. Product draft protections are unchanged. Per-sample blankResetDiagnostics retains counts and blankCompleted only, without dialog messages, URLs, headers, claims or bodies. The reset policy version is a comparison condition; earlier reports remain independent and cannot be backfilled. Actual new-source full lab must establish whether this mechanism accounts for the historical merchant warm failure; the stage signature alone is not a causal API diagnosis.

### Separate operations release assessment

The collector retains a complete slow run without treating numeric failure as collection failure. CI now runs `assert-operations-assessment.mjs REPORT_PATH EXPECTED_MEASURED_SHA [CANDIDATE_HEAD [PR_BASE_SHA]]` after collection, even when a prior collection step failed. Missing or ambiguous report paths fail; all raw artifacts still upload.

This prerequisite requires the recorded and recomputed assessment to pass, exactly48 navigation/8 interaction/24 equivalent reads, correct roles, verified navigation, LCP≤2500ms and CLS≤0.1 group medians, owned cleanup, an empty recorded source diff and a clean current checkout. The checkout must be the expected measured commit. For PR merge commits, both ordered parents must match the supplied base/head and the measured tree must equal the candidate tree. A merge that changes candidate content requires revalidation of an updated candidate; a matching SHA label is insufficient. Checkout depth2 retains the parent objects needed for this verification.

This gate does not invent latency budgets, accept `MEASURED_BUDGET_NOT_SET` as a latency PASS, establish cloud SLOs, or replace hosted acceptance. It does not rerun, discard, or reclassify a slow original sample. Both original push and PR reports remain independently required by the release checklist.
